5.4 Coding and Pseudocodes

5.4.1 Introduction

The coding phase converts system design models into executable software through frontend user interface components, geospatial coordinate mappers, backend services, satellite-data processing, U-Net inference, and physics-based fire-spread simulation. The frontend manages user interactions and visual presentation across both continental 3D globe (CesiumJS) and local ecosystem (Three.js) scales. The Python inference service processes multi-spectral model inputs to generate burned-area segmentation outputs. In parallel, independent simulation models calculate hypothetical fire progression parameters based on environmental and terrain conditions without altering the deep learning architecture.

5.4.2 Programming Style

The programming style used in the Digital Twin-Based Wildfire Detection and Prediction System focuses on keeping the code simple, organized, and easy to maintain. The application is divided into separate modules for frontend components, geospatial visualization, satellite-data processing, U-Net inference, and fire-spread simulation. This modular approach makes it straightforward to understand the logic and update individual modules without affecting the rest of the application.

  • Names: Meaningful names are assigned to files, functions, and components based on their explicit responsibility. For example, UNetDetectionPanel.tsx displays detection-related metrics and confidence masks, while FireSpreadPanel.tsx provides interactive controls for fire-spread analysis. unetInferenceService.ts coordinates inference communications, while fireSpreadModel.ts houses the directional rate-of-spread simulation mathematics. These explicit identifiers streamline code navigation and readability.
  • Control Constructs: Structured conditional statements evaluate coordinate validity, satellite imagery availability, and process status. Iterative loops support repeated mathematical execution, such as advancing fire front progression across successive future simulation horizons and calculating radial expansion across 36 directional sectors.
  • Information Hiding: Each module manages its domain responsibilities without leaking internal mechanics to surrounding components. For example, frontend panels present output visualizations without performing matrix tensor transformations or differential spread equations themselves. The inference service abstracts API communication, while the spread model isolates physics calculations.
  • User-Defined Types: TypeScript interfaces formalize data structures passed between components and services (e.g., Coordinates, EnvironmentalInfo, DetectionResult, and SpreadResult). This enforces type safety at compile time, prevents schema discrepancies, and enhances codebase maintainability.
  • Nesting: Nested control sequences guarantee proper execution order. For instance, the system validates that satellite coverage exists for a geographic bounding box before invoking deep learning segmentation routines. Similarly, barrier clamping checks are nested within radial sector ray-casting loops.

5.4.3 Pseudocodes

Algorithm 5.1: Satellite Data Validation and U-Net Burned-Area Detection
Input: Target location C_target (Coordinates: lat, lon), Decision threshold τ = 0.65
Output: Detection result R_detect (DetectionResult: binary mask M_bin, burned area %, vector boundary) 
BEGIN
  1.  // Step 1: Input validation and data availability check (Nesting & Control Constructs)
  2.  IF C_target.latitude is NULL OR C_target.longitude is NULL THEN
  3.    RETURN Error: "Invalid geographical coordinates provided."
  4.  END IF

  5.  satelliteData ← unetInferenceService.checkDataAvailability(C_target)
  6.  IF satelliteData.isAvailable == FALSE THEN
  7.    RETURN Error: "No suitable Sentinel-2 multi-spectral imagery found."
  8.  END IF

  9.  // Step 2: 15-channel feature preparation (Information Hiding)
  10. rawBands ← unetInferenceService.fetchBands(C_target)    // 12 bands: B01-B09, B11, B12
  11. ndvi ← (rawBands.B08 - rawBands.B04) / (rawBands.B08 + rawBands.B04 + 1e-7)
  12. nbr  ← (rawBands.B08 - rawBands.B12) / (rawBands.B08 + rawBands.B12 + 1e-7)
  13. ndri ← (rawBands.B04 - rawBands.B02) / (rawBands.B04 + rawBands.B02 + 1e-7)
  14. tensor15ch ← StackAndNormalize(rawBands, ndvi, nbr, ndri)

  15. // Step 3: U-Net deep learning model inference
  16. probabilityMap ← UNetModel.predict(tensor15ch)
  17. countBurned ← 0

  18. FOR EACH pixel (x, y) IN probabilityMap:
  19.   IF probabilityMap[x, y] >= τ THEN
  20.     M_bin[x, y] ← 1
  21.     countBurned ← countBurned + 1
  22.   ELSE
  23.     M_bin[x, y] ← 0
  24.   END IF
  25. END FOR

  26. // Step 4: Package results into strongly-typed output
  27. R_detect.burnedPercentage ← (countBurned / TotalPixels) * 100.0
  28. R_detect.burnedAreaHa ← countBurned * 0.01             // 1 pixel (10m x 10m) = 0.01 ha
  29. R_detect.vectorBoundary ← VectorizeMaskToGeoJSON(M_bin)
  30. R_detect.status ← "SUCCESS"

  31. RETURN R_detect
END
Algorithm 5.2: Multi-Time-Step Fire-Spread Simulation and Cesium 3D Visualization
Input: Ignition point P_ign (Coordinates), Weather E_env (EnvironmentalInfo), Horizons H = [0, 1, 2, 6, 12, 24]
Output: Simulation result S_spread (SpreadResult: per-time-step radial expansion and 3D terrain layers) 
BEGIN
  1.  // Step 1: Validate ignition point combustibility
  2.  IF fireSpreadModel.isWaterOrNonBurnable(P_ign) == TRUE THEN
  3.    RETURN Error: "Ignition point is located on water or non-combustible surface."
  4.  END IF

  5.  // Step 2: Compute baseline fuel moisture and Rothermel damping factor
  6.  fuelMoisture ← fireSpreadModel.computeEMC(E_env.temperature, E_env.humidity)
  7.  dampingEta ← fireSpreadModel.computeMoistureDamping(fuelMoisture)
  8.  baseROS ← 2.5 * dampingEta                         // Base rate of spread in m/min

  9.  // Step 3: Loop through each simulation horizon (Control Constructs & Loops)
  10. FOR EACH horizon t IN H:
  11.   boundaryPoints ← EMPTY_LIST

  12.   // Sub-step: Calculate directional propagation across 36 sectors (Δθ = 10°)
  13.   FOR sectorAngle FROM 0 TO 350 STEP 10:
  14.     phiWind ← fireSpreadModel.calculateWindFactor(E_env.windSpeed, E_env.windHeading, sectorAngle)
  15.     phiSlope ← fireSpreadModel.calculateSlopeFactor(P_ign, sectorAngle)
  16.     rosSector ← baseROS * phiWind * phiSlope
  17.     intendedRadius ← rosSector * 60.0 * t          // Expansion distance in meters

  18.     // Barrier checking: Halt spread if water body or road is encountered
  19.     clampedRadius ← intendedRadius
  20.     FOR dist FROM 25.0 TO intendedRadius STEP 25.0:
  21.       probePt ← ProjectCoordinate(P_ign, dist, sectorAngle)
  22.       IF fireSpreadModel.isWaterOrNonBurnable(probePt) == TRUE THEN
  23.         clampedRadius ← dist - 25.0
  24.         BREAK                                      // Clamp fire front at barrier edge
  25.       END IF
  26.     END FOR

  27.     boundaryPoints.APPEND(ProjectCoordinate(P_ign, clampedRadius, sectorAngle))
  28.   END FOR

  29.   // Step 4: Render updated fire perimeter on CesiumJS 3D terrain
  30.   perimeterPolygon ← CreatePolygonHierarchy(boundaryPoints)
  31.   CesiumViewer.renderSpreadLayer(perimeterPolygon, clampToGround=TRUE)
  32.   S_spread.timesteps[t] ← {perimeter: perimeterPolygon, burnedArea: CalcArea(boundaryPoints)}
  33. END FOR

  34. RETURN S_spread
END

5.5 Summary

The system integrates Sentinel-1 SAR and Sentinel-2 satellite data processing with a trained U-Net model to identify burned areas and generate detection masks. Environmental and geographical information supports fire-spread simulation and risk-zone analysis, while CesiumJS provides interactive 3D visualization of terrain, affected regions, and simulated fire progression. The dashboard presents detection results, environmental conditions, and wildfire scenarios in a user-friendly interface. The modular architecture, structured coding practices, and TypeScript support improve readability, maintainability, and flexibility. Overall, the implementation provides an integrated platform for wildfire monitoring and analysis, although further validation and improved environmental data integration are needed to enhance the reliability of fire-spread simulations.
